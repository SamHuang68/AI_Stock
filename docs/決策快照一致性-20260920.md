# 決策快照一致性

本次接續架構審查，修正「決策尚未儲存卻回報發布成功」與畫面識別語意錯誤。既有行情、預警計算及個人化決策沿用原路徑，儲存邊界獨立到 `server/decision_store.py`。

## 發布與恢復

1. 在既有 `decision_history.db` 保存待發布意圖，包含決策、行情、重建輸入、預警記憶體來源、規則摘要及評估時間。
2. 預警庫以 `publication_id` 查收據；未處理才執行生命週期。狀態、觀測、事件、試驗與完整回傳收據在同一個預警 SQLite 交易完成。重播回傳原結果，不重新累加命中次數或刷新效期。
3. 決策庫在同一個 SQLite 交易提交完整決策、輸入、遞增修訂、歷史及通知待辦，並刪除意圖。提交成功才更新記憶體及成功時間。
4. 提交失敗保留前次已提交版本；`/pulse` 回應 HTTP 503，不把未提交摘要寫入成功快取。下一次發布先恢復待處理意圖，再依行情更新開始時間拒絕逆序結果。
5. 程序重啟後，讀取可載入最後已提交資料與原輸入；讀取只依原觀測時間重新判斷效期，不推進預警、不恢復意圖，也不傳送通知。

決策庫與預警庫是**可恢復協定，並非跨資料庫原子交易**。預警自己的查詢端點可能在決策提交前看見已推進的預警；決策全文、Pulse 摘要及決策歷史只使用已提交決策。待恢復意圖的規則摘要不同時，停止新發布並保留診斷，避免以新規則重算舊意圖。

`snapshotId` 由完整輸入、計算結果、預警來源與規則摘要決定；`revision` 是資料庫持久遞增值。相同重播不重複提交；舊識別不讓目前修訂倒退。API 回傳副本，呼叫端修改不會污染內部狀態。

最後 500 筆決策快照沿用既有歷史保留上限。預警收據在決策成功提交後才確認，僅清除超過最近 500 筆的已確認收據；未確認收據保留供恢復。完成的通知嘗試隨已淘汰決策清理，失敗與中斷紀錄保留供檢查。

## 通知邊界

通知仍使用既有設定與傳送器。每筆工作先記錄 `attempted`，再進入通知流程；不自動重送已嘗試工作。這可避免重啟重複通知，但不是外部傳送的恰好一次保證：若程序在記錄嘗試後、實際傳送前中斷，可能未送達。`attempted`／`failed` 及原逐通道結果供追查，健康資訊會顯示各狀態數量。已提交資料的讀取不等待通知網路。

## 畫面契約

- 「快照／修訂」使用後端識別與持久修訂；缺少時顯示未提供。契約版本獨立顯示，原前端雜湊保留並改稱畫面識別。
- 市場範圍一致與摘要／全文核對分開。相同已提交識別、修訂、規則及效期視圖，且核對內容相同，才顯示一致；缺少全文不推定一致。
- 個人化衍生結果標記 `ephemeral`，只保留來源 `parentSnapshotId`，不冒充已提交正式快照。
- Pulse 金框以自己的摘要為準，其他頁面的衍生決策不覆蓋它。
- `/sync/status` 標為歷史資料同步，最新錯誤優先顯示，並保留最後成功時間。

## 驗證與剩餘邊界

新增真實暫存 SQLite 故障注入、並行發布、程序狀態重設、原物件隔離與前端行為測試。涵蓋儲存失敗、未確認收據保留、重播、規則不符停止恢復、損壞識別拒絕讀取、個人化來源、效期降級、通知失敗明細與讀取不等待通知。另以獨立程序重啟、固定資料瀏覽器頁及正式雙端驗收補充證據。

這輪不宣稱完成舊 S2 的全部更新佇列架構：`GET /pulse` 遇到快取未命中仍會建置與發布，後續可再將更新工作與讀取已提交資料拆開。既有歷史列沒有快照識別者保持原樣，不補造識別。發布與重啟仍依既有單一服務程序管理；不把程序內發布鎖描述為多主機共用寫入鎖。

本機完整回歸為 630 項 Python 測試，626 項通過、4 項依既有條件略過；35 組 JavaScript 自測全部通過，編譯、建置順序及 HTML 建置通過。固定資料瀏覽器頁的五情境斷言通過，已查看桌機及 390px 手機直式版面。精確提交、CI、部署版本及資料保留結果記錄於本次交付驗證紀錄。
