## D4：根因與流出原因

**發生根因一：有效日線的位置被誤當交易日。** 實際 Yahoo `regularMarketTime=1792128805`（10/16 13:33:25），現價 `47111.26`；最後三根日 K 的收盤為 `48625.828125、46969.87109375、null`。10/15 資料存在，缺值的是 10/16。`refreshMktBar` 過濾空值後固定取倒數第二筆，因此錯取 10/14。

**發生根因二：跨來源只按秒數排序，阻止官方校正。** Yahoo 備援先進入共用行情。MIS 正確報價為同日 13:33:00，比 Yahoo 早 25 秒；合併器先拒絕較早時間，尚未判斷來源品質就丟棄官方值。自然事件確認順序為 `chart-fallback → pulse → snapshot`，後兩個事件之後 store 仍保留錯前收。正常載入、一日、半年與等待後共五次觀測皆精確重現使用者錯值。

**擴散路徑：** 共用 store 同時驅動標頭與行情列，完整但錯誤的備援也讓原 `/twindex` 校正提前返回。兩處一致因而不是正確性的證據。

`git blame` 確認本輪前次提交 `63b133279e5c21298d0cfeb0c17d21a56a6831d0` 引入共用備援發布及這個合併順序；倒數第二筆的舊計算法原先已存在。前次整組對齊將舊計算錯誤擴散到主圖，且未能接受後續官方校正。

**流出根因：** 前次瀏覽器驗收從產品 store 反算期望，再比同一 store 驅動的畫面；共同錯誤可以全部通過。選取標的時還主動呼叫 `MarketData.refresh()`，未保留自然請求時序。只覆蓋官方先到後拒絕備援，漏掉備援先到且時間晚 25 秒。固定案例未包含當日日 K 空值。主控沒有獨立比對市場資料就回報修正完成，是驗收設計與回報責任缺口。

**系統原因：** 原欄位完整性與時間新舊被當作足夠可信條件；價格、基準日期、來源順位沒有一起驗證。修正與證據要求都必須落在這些契約，不能只改畫面文字。

## D5：永久修正

- 加權、櫃買依現價所屬交易日選最後一筆較早日期的有效日 K，不固定使用倒數第二筆；保留既有 metadata 前收與日線備援能力。
- 現價缺值時，價格與時間一起退回最後有效日 K，前收也依該日期選取。
- 只有實際從歷史日 K 選出的前收才附 `referenceDate`；metadata 只有數字時日期仍未知，不憑數字相等推定。
- 同一臺北交易日，正式加權／櫃買行情可覆蓋日線備援，不受不同供應商秒差阻擋；同品質與跨日仍保留時間排序。台指期不適用新增例外。

審查提出缺現價日期與 metadata 日期兩項 P2，已修正並加入局部案例。未移除功能或操作入口。
